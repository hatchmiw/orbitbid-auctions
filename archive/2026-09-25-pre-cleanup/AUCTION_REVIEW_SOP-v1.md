# Auction review operating procedure — required reading

**Before every auction review, resumption, photo workflow change, or new batch:** read this file, the repository README, the auction's `REVIEW.md`, the current catalog/review status, and the relevant workflow YAML. The repository files, not chat history, are the authoritative checkpoint. If any instructions conflict, stop and resolve the discrepancy rather than silently changing the workflow.

## Non-negotiable photo handling

1. **Reuse the existing temporary auction photo artifact first.** Check GitHub Actions for a successful `Run OrbitBid Auction` or `Mirror auction photos` run and its `orbitbid-<auction-id>-photos` artifact. For auction 1879, also check `orbitbid-1879-review-photos`. Inspect artifact manifests and confirm that all requested lot IDs, image counts, original source URLs and per-lot `review.jpg` sheets are present and correctly mapped. A successful workflow alone is not proof that an artifact is still available.
2. **Never redownload merely because a new review batch begins.** Use existing original photos and review sheets from the temporary artifact for any number of successive batches. If the artifact is inaccessible, expired, incomplete or has bad provenance, first establish exactly what is missing and only then rebuild the minimum necessary material from the permanent `lots.json` source URLs. State why a rebuild is needed. Do not infer image identity from neighboring lots.
3. **Do not commit original photos, contact sheets, review images, ZIP archives or other photo copies to Git.** Store them in temporary GitHub Actions artifacts. Only catalog metadata, original image URLs, manifests/provenance *without embedded images*, batch selections, assessments, valuations and review checkpoints belong in the repository. Existing historical commits may still contain old images; do not repeat this pattern.
4. Use the established auction photo-retention policy: latest scheduled lot close plus seven days, subject to GitHub's 90-day artifact maximum. Check that a usable artifact exists before promising visual inspection. If a prior artifact is expired, explicitly report that before rebuilding it.
5. `build-source-verified-previews.yml` is a **recovery path**, not the normal per-batch process. Do not modify `review_requests.json` to trigger it until the artifact-first check has failed and the recovery is justified. Its outputs must remain temporary artifacts.

## Resuming and reviewing

1. Read `auctions/<id>/REVIEW.md`, `catalog-review.csv`, existing batch reports and the queue. Count distinct reviewed lot IDs rather than assuming every queued lot is inspected or valued. Preserve completed batches; never duplicate them.
2. For each selected lot, inspect **every original source photo** (not just the catalog's first photo or an abbreviated title). Record exact lot ID, source-image count, visible identification, condition, missing components, uncertainty and relevant handling/safety concerns. When only contact sheets are available, clearly distinguish them from full-resolution source inspection.
3. Keep states separate: queued; photos available and provenance verified; visually inspected; assessed/valued; merged into master CSV/watchlist. Do not claim a later state without evidence.
4. Save durable per-lot findings and the exact checkpoint to GitHub after each manageable inspection pass. Merge reviewed records by unique lot ID, preserving the 487-row master catalog and existing 200 valued lots for auction 1879 unless verified changes warrant an update. Review statuses, counts, provenance and documentation must agree.
5. Valuation: distinguish visual condition from proven function. Use conditional gross resale ranges and hammer ceilings only where supported; account separately for premium, tax, removal, shipping, repairs and sale fees. Never invent sold comps, current bids or functional tests.
6. If interrupted, re-read the repository and the latest successful workflow/artifact state; resume from committed lot IDs and findings, not from a prior assistant's claimed progress. Report precisely what has and has not been done.

## Mandatory preflight on every execution

Before running scripts or making photo-related commits, explicitly verify and record: (a) current auction and lot IDs; (b) current catalog count and existing completed IDs; (c) existing artifact run ID, expiry and manifest coverage; (d) whether any download is actually needed; (e) whether planned Git changes contain *only* text/metadata; (f) intended checkpoint updates. If any check fails, stop or document a targeted recovery. A workflow success must not be represented as a completed human visual inspection.

## Mandatory artifact-download procedure — validated 2026-09-25

**This section is required before every photo-inspection or resumed review. Do not infer tool limitations or improvise a replacement workflow without first checking this procedure.** The Pioneer repository's `.github/CHATGPT_RUNBOOK.md` documents the proven precedent (auction 779190, lot 321): photo-batches manifest → GitHub Actions artifact ZIP → extracted original JPG bytes → actual visual inspection.

1. Read this SOP, `AGENTS.md`, root `README.md`, the auction's `REVIEW.md` and applicable workflow YAML. Read the current catalog and completed-lot checkpoint. Consult Pioneer runbook when troubleshooting photo retrieval.
2. List **existing** successful GitHub Actions run artifacts and confirm artifact IDs, byte sizes, expiry and manifest lot/photo coverage. Use the GitHub connector's **`download_workflow_artifact({repo_full_name, artifact_id, file_name})`** action for ZIPs. The generic `fetch`/`fetch_file` action is not the artifact downloader. A ZIP download yields a connector file reference and, when materialized, a working-container ZIP path; inspect the ZIP, manifest and per-lot originals. Forward actual JPG bytes to vision. Seeing metadata, filenames, URLs or a contact sheet is not full-resolution original-photo inspection.
3. **512 MiB per-download limit:** the GitHub connector rejects an artifact larger than **536,870,912 bytes**. This is a size limit, **not** an inability to download binary ZIPs. Prefer existing split artifacts below the limit. Do not ask the user to download/upload an archive, scrape original images again, or commit duplicate image files while usable split artifacts exist.
4. **Auction 1879 verified artifact map (2026-09-25):** full archive run `36039298628`, artifact `10825787468`, 1,551,140,605 bytes (too large for one connector download); batch 07 run `36087152300`, artifact `10844646656`, 85,614,778 bytes (**successfully downloaded and ZIP contents verified on 2026-09-25**); split batches 08–13 run `36087642169`: batch 08 artifact `10844397014` (65,142,136 bytes), 09 `10844157362` (109,176,624), 10 `10844052609` (118,941,875), 11 `10844227160` (136,762,572), 12 `10844526785` (374,952,135), 13 `10843977621` (55,392,055). All were unexpired when checked September 25; **recheck at every resumption**. Batches 01–06 may require an existing separate artifact or a targeted artifact-only split from the existing full archive; first locate and verify it, not a new source download.
5. Select the smallest existing artifact(s) covering the target lot IDs. Extract only their lot JPGs, confirm lot ID/image count/source provenance against `lots.json` or the artifact manifest, inspect **all originals** for selected lots and write findings to the authoritative text-only review. Keep contact-sheet-level and all-original-photo-level statuses distinct. Do not report all-photo review until JPG bytes actually reach vision.
6. If no usable sub-512 MiB artifact covers the requested lot, inspect the existing artifact-splitting workflow `.github/workflows/review-from-existing-artifact.yml`. Prefer an **artifact-only split** from the already-mirrored full archive, with no OrbitBid redownload and no photo commits. Confirm workflow inputs and exact missing lot coverage before running. If this established route fails, **discuss the proposed alternative and its tradeoffs with the user before deviating**; do not silently change storage, scrape strategy, or review scope.
7. At the start of every resumed pass, log the SOP version/commit consulted, artifact/run IDs and size/expiry, the selected lot IDs and original-photo counts, and the exact completed checkpoint. Do not substitute generic status narration for a durable GitHub checkpoint.

**Failure taxonomy:** artifact expired/missing; artifact over connector limit; connector ZIP download failure; ZIP materialization/extraction failure; manifest or lot/photo mismatch; image bytes not forwarded to vision; visual review incomplete. Report the actual failure and try the documented recovery in order. A successful ZIP download alone does not complete a visual review.

## Completion is the stop condition — 2026-09-25

For an explicitly requested full auction review, **completion of every lot is the stopping condition, not a checkpoint or an arbitrary batch size**. Open and visually examine **each numbered original source photograph separately** for each pictured lot; do not substitute montages, contact sheets, image filenames or metadata. Examine and record every lot, including explicit no-photo status for unpictured lots. Record item identity, components, condition, uncertainty and pickup/safety issues in the master catalog by exact lot ID. Save and commit verified work after every 20 completed lots (or earlier if needed to prevent loss), then **immediately proceed to the next unreviewed lot without awaiting another user message**. Preserve previous notes and validated research; never assign unsupported prices. Check the 487-row catalog integrity after each commit. Stop before full completion only for a genuine technical blocker or execution limit; preserve an exact resume checkpoint naming the last completed lot, next lot and photograph, remaining count, artifact/run ID and actual blocker. Do not represent an interrupted review as completed or imply background work continues after the response ends. If the documented artifact path fails, use its prescribed recovery; discuss any deviation with the user before changing methods.
